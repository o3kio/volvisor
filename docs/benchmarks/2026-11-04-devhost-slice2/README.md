# Control-plane benchmark evidence — 2026-11-04 D3 slice 2, single-host development lab

This bundle records the required clean-tree measurement at the final
Phase D D3 slice-2 commit. Slice 2 releases the provider state lock for
attach/detach/report and coalesces concurrent captures into one physical
save; this run measures the resulting shape. It is a **single-host
development-lab** record: one `volvisord` on one host, a disposable
loop-backed LVM volume group, control-plane HTTP only. It is **not**
production evidence, **not** a data-path benchmark, **not** an SLA, and
**not** the issue's 24-hour soak (a shortened 25-minute soak ran).

  (`volvisord c4b0b13`).

## What this run verifies

The run exists to check the slice-2 write path under sustained churn and the
same 1/8/32/128 sweep as the Phase C baseline, not to establish capacity:

- **The throughput ceiling did not move.** c1/c8/c32/c128 measured
  **1845.526 / 3410.746 / 858.371 / 237.088 ops/s**, versus **1952.155 /
  3493.445 / 862.937 / 235.502** at `aab773b` (−5.5 / −2.4 / −0.5 / +0.7 %).
  This run does not support a throughput-gain claim.
- **Read latency fell sharply.** Read p95 at c32 fell from **179.332 ms** to
  **1.188 ms**, and at c128 from **1288.505 ms** to **197.815 ms**. Reads
  were already snapshot reads; the improvement is consistent with async
  waiters no longer pinning runtime workers, but the harness does not
  attribute delay.
- **The write tail got worse at high in-flight.** Write p95 at c32 rose from
  **388.84 ms** to **590.847 ms**, and at c128 from **1552.261 ms** to
  **6330.548 ms**. Synchronous `grow` still holds the state lock across the
  LVM resize while async writers yield; the harness does not attribute the
  delay, so this is an observation, not a proven cause.
- **The shortened soak completed 6,929,746 ops at 4619.824 ops/s** with
  **0 HTTP errors and 0 attachment conflicts**; the 77 network errors are
  client reconnects at the planned restart. The post-fix baseline ran
  5,424,744 ops at 3616.49 ops/s (+27.7 %). RSS grew **+2,943,816 KiB**
  (peak **3,236,184 KiB**), versus **+1,780,896 KiB** at `aab773b`; this is
  a single non-fixed-dataset run and is **not** a capacity claim.
- **Provider state stays bounded** at **3,401 bytes** end (**3,684 B** max),
  and the journal stays bounded at **43,412,309 bytes** end
  (**75,497,689 B** max).
- **Restart replay is healthy.** The mid-soak restart listed 4/4 volumes in
  **0.547 s** with unchanged state and journal sizes; pre/post-soak restarts
  recovered in 0.082–0.527 s.
- **The generation fence and crash semantics are exercised by the test
  suite** at `c4b0b13`, not by this harness. This harness is a load
  generator; it is not a crash-consistency test.

## What it also exposed (open residuals)

These are findings, not fixes, and they are not production claims:

- **Write-tail latency at high in-flight.** c32/c128 write p95 is worse than
  the baseline while read p95 is much better. The overall ceiling is
  unchanged. A follow-up should attribute the stall before claiming a
  regression fix; it may be the synchronous `grow`/state-lock residue, a
  coalescing/fairness effect, or the harness mix.
- **RSS high-water is higher and remains unresolved.** RSS peaked at
  **3,236,184 KiB** (≈3.09 GiB) and ended at 3,108,756 KiB, versus
  2,323,028 KiB / 1,950,048 KiB in the baseline. A leak is neither proven nor
  ruled out. No RSS cap or fix is claimed.
- **The default INFO daemon log is unbounded.** The ~30-minute run produced
  **2,306,552,235 bytes** (≈2.15 GiB) and **8,575,422** lines (8,574,997
  INFO, 425 WARN) with no rotation. The committed copy is
  `raw/daemon.daemon.log.gz` (60,577,546 bytes compressed). Logging volume is
  an operational finding, not a durable-state defect.
- **The cap-32 admission probe shed load this run.** 77 requests returned
  `503` under the probe's configured 1 s queue timeout, unlike the baseline
  (0). The default-cap sweep had 0 `503`/`429`. The probe is diagnostic and
  is not a capacity result.
- **The 25-minute soak is not the 24-hour soak.** The 24 h soak is **NOT
  RUN**.

## Capacity in one line

At 30 s per tier with the product default admission cap of 256, measured
throughput was **1845.526 ops/s at 1 in-flight**, **3410.746 ops/s at 8**,
**858.371 ops/s at 32**, and **237.088 ops/s at 128**; overall p95 latency
was **1.457 ms → 7.467 ms → 197.17 ms → 3553.448 ms** respectively. The
25-minute soak sustained **4619.824 ops/s**. This is not a throughput
improvement over the baseline; see [REPORT.md](REPORT.md) §4–§5 and §9 for
the split read/write latencies and caveats.

## What this bundle is not

- **Not production evidence** and not a support-matrix change.
- **Not multi-host.** There is no second physical host, no real Ceph, no
  DRBD, no physical-disk LVM, and no independent failure domain.
- **Not a data-path benchmark.** No guest I/O, no block-data proxying, no
  filesystem or fio workload, no disk IOPS/latency.
- **Not the 24-hour soak.** The shortened soak ran for 25.0 minutes, with one
  mid-run restart.
- **Not an SLA or capacity plan.** All numbers are one host, one loop-backed
  VG, one process. The loop image and the journal/state files share the same
  ext4 filesystem.
- **Not a durability proof.** It exercises acknowledged control-plane writes;
  it does not prove crash consistency or data-path durability.
- **Not a throughput win.** The ceiling is unchanged and the write tail is
  worse; do not cite this bundle as an efficiency improvement.

## Reproduction

```bash
# Build the release binary first (REPORT.md §3), then use a fresh run dir.
sudo scripts/bench/run-all.sh \
  --run-dir /tmp/opencode/volvisor-bench-$(date -u +%Y%m%dT%H%M%SZ) \
  --skip-build --sweep-seconds 30 --soak-minutes 25
```

Use a **fresh** run directory: `run-all.sh` appends to an existing run's logs
and does not clean its journal/state. The recorded run used
`/tmp/opencode/volvisor-bench-slice2-20261104T231012Z`; that workspace copy is
now populated and must not be reused verbatim. The committed bundle is the
durable evidence copy. Verify the bundle with
`sha256sum -c MANIFEST.sha256`. Re-generate the comparison with:

```bash
python3 scripts/bench/compare.py \
  --before docs/benchmarks/2026-11-04-devhost-postfix \
  --after docs/benchmarks/2026-11-04-devhost-slice2 \
  --out /tmp/opencode/slice2-compare
```
