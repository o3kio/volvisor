## What this run verifies

The run exists to confirm, with the same 1/8/32/128 sweep and 25-minute soak
as the prior runs, that the capacity-sample convoy and the state-lock grow
serialization are gone, while capacity atomicity and the durable grow intent
remain.

- **Throughput improved at every tier and in the soak.** c1 **1,729.154 →
  1,825.419 ops/s (+5.57%)**, c8 **3,118.787 → 3,846.899 (+23.35%)**, c32
  **1,830.005 → 2,609.257 (+42.58%)**, c128 **440.376 → 655.326 (+48.81%;
  one sample at the high end of the observed 599.405–655.326 range, see
  below)**; the 25-minute soak **4,425.586 → 4,756.348 ops/s (+7.47%)**.
- **The non-grow tail collapsed.** c32 write p95 **206.203 → 82.927 ms
  (−59.78%)**; c128 attach/report/detach p95 **3,200.094 / 3,572.972 /
  3,642.250 → 211.323 / 194.448 / 205.577 ms**; c128 read p95 **87.276 →
  6.584 ms (−92.46%)**.
- **No sweep errors.** All **274,352** default-cap sweep requests returned
  2xx; real grows ran (4 / 32 / 128 / 438 at c1 / c8 / c32 / c128). The
  c128 run completed 25,816 ops versus 13,317 at `8029df8`.
- **The c128 aggregate write p95 is not like-for-like.** The candidate's
  **5,078.906 ms** write p95 is a grow value (its slowest non-grow write is
  819.067 ms); the comparator's **3,413.886 ms** is an attach/report/detach
  value (its slowest grow is 600.611 ms). Grow completions rose **255 → 438
  (+71.8%)** and grow completion rate **8.433 → 11.118/s**, but the LVM-bound
  queue deepened: grow p50 **338.017 → 8,338.505 ms**, p95 **498.894 →
  19,633.371 ms**. The grow tail is **not fixed**; see
  [REPORT.md](REPORT.md) §11.
- **The all-operation p95 still improved.** c128 overall p95 **1,836.718 →
  117.870 ms (−93.58%)**; only the write-only p95 moves the other way,
  because its top 5 % becomes the grow queue.
- **The capacity protocol is test-covered, not load-proven.** The
  allocation-epoch reservation, publish under the state lock, retry cap,
  per-volume drive guard and durable-intent recovery are exercised by the
  workspace tests at the measured SHA; this harness is a load generator,
  not a crash-consistency test.
- **The shortened soak is healthy.** **7,134,530 ops at 4,756.348 ops/s**,
  with **0 HTTP/provider errors** and no 409s. The **81 network errors**
  (78 `ConnectionRefusedError`, 2 `RemoteDisconnected`, 1 `BrokenPipeError`)
  are client reconnects at the planned mid-soak restart; the `8029df8` soak
  recorded 46 of the same class. The mid-soak restart listed 4/4 volumes in
  0.629 s (stop 0.342 s).
- **Provider state stays bounded** at 3,147 B end (4,083 B max); the
  journal ended at 49,560,395 B (vs 75,496,834 B at `8029df8`). RSS peak was
  2,361,868 KiB (vs 2,538,456 KiB); a leak is neither proven nor ruled out.
- **Restart replay is healthy.** Pre-soak 0.081–0.102 s, mid-soak 0.629 s,
  post-soak 0.606–0.608 s; all `OK`.

## Same-SHA sensitivity (non-evidence)

Two further clean sweeps at the same SHA and binary, with the same cumulative
sequence but `--skip-soak`, measured c128 **599.405** and **614.158 ops/s**
(first 30 s: 773.0 and 787.9 ops/s), with aggregate write p95 **7,478.820**
and **7,586.304 ms** (both grow values; non-grow max 1,200.035 and 882.881
ms), grow shares 6.33 % and 6.05 %, and grow p50/p95 9,078.429/16,868.315
and 9,773.824/16,165.053 ms. The published run measured 655.326 ops/s
(851.3 in the first 30 s) and 5,078.906 ms. All three agree on the non-grow
path (attach/report/detach p95 179–228 ms) and the seconds-long grow queue;
they differ in both completion-inclusive throughput and the aggregate p95,
because the realized grow share moves between 5.81 % and 6.33 % around the
5 % boundary. The primary is one sample at the high end of the observed
throughput range (+36.1 % to +48.8 % versus the comparator, all above it);
it was not chosen from the repeats, which were run afterwards. The repeats
are **not** part of this bundle and are not evidence; all values are stated
so neither is cherry-picked.

## What changed in the code

`a3ea5abf` removed the grow capacity-sample convoy. Capacity is sampled
outside the provider state lock, an allocation epoch invalidates a sample
that raced with any allocation, and the per-VG reservation and durable grow
intent are published under the state lock. A bounded optimistic-retry cap
turns sustained churn into a typed refusal instead of a loop. `6519068`
removed the provider-level grow semaphore after a same-commit A/B diagnostic
showed it added queue delay without raising the LVM-bound completion rate.
`4290b84` then fixed two Medium defects found by adversarial review: a create
attempt whose `lvcreate` failed or was adopted now bumps the allocation
epoch on every post-attempt path, and the grow publish no longer discards a
state-lock error (it keeps the epoch bump and reservation drop on both paths
and logs the degraded path).

## What it also exposed (open residuals)

These are findings, not fixes, and they are not production claims:

- **c128 grow queue/tail is unresolved.** Grow completions are
  LVM-per-VG-bound at ~11.1/s; 128 simultaneous resizes queue for seconds.
  The aggregate c128 write p95 is composition- and run-sensitive. Do not
  claim the grow tail is fixed.
- **c8/c32 grow latency also rose** (grow p50 280.104 → 569.102 ms at c8;
  292.593 → 2,358.653 ms at c32) even though the grow share is too small to
  enter those write p95s. This is queue depth/burstiness, not a measured
  per-request slowdown.
- **Shared-cap grow starvation posture.** The daemon admission cap is shared
  with reads and attaches, mutations have no execution timeout, and rate
  limiting is off by default. A sustained grow flood can shed reads/attaches
  with `503` after the queue timeout. Documented in
  `docs/admission-control.md`; not solved here.
- **Create still holds the state lock across its `vgs` sample and
  `lvcreate`/`lvs`.** This is the same defect class the epoch protocol
  removed for grow; the mixed sweep has no create/delete, so it is not
  measured here.
- **Cumulative-run RSS/journal effects are not attributed.** The c128
  segment starts at 702,104 KiB RSS and a 13.4 MB journal in the full
  sequence, versus much lower values in a fresh-daemon diagnostic. No cause
  is claimed.
- **`block_in_place` worker-set cost is not measured.** Interval
  reconstruction from the recorded operation start/end times shows 128
  concurrent grows at c128 (8029df8: 6); the runtime may transiently grow
  its worker set. The observed RSS high-water is recorded, not attributed.
- **Pre-existing residuals remain.** Move admission is outside the epoch
  protocol; retry `resume_pending_grow` and `settle_failed_lvextend` run
  `lvs` under the state lock; in-doubt journal intents accumulate across
  restarts; duplicate-grow refusals are journaled terminal failures; the
  default INFO daemon log is unbounded (2.24 GiB raw here).
- **The 25-minute soak is not the 24-hour soak.** The 24 h soak is **NOT
  RUN**.

## Capacity in one line

At 30 s per tier with the product default admission cap of 256, measured
throughput was **1,825.419 ops/s at 1 in-flight**, **3,846.899 at 8**,
**2,609.257 at 32**, and **655.326 at 128** (completion-inclusive; the first
30 s window completed **851.3 ops/s** at c128). Overall p95 latency was
**1.457 → 7.478 → 46.913 → 117.870 ms**. The 25-minute soak sustained
**4,756.348 ops/s**. This is a measured reduction of the capacity-sample and
state-lock convoy, not a blanket throughput claim and not a fix for the
c128 grow tail.
