## 1. Scope and what changed

Phase E releases the single provider state mutex across the long external
LVM commands of create and delete, keeping the durable intent as the
fail-closed recovery anchor.

- **E1 (`8cfa4c2`) — delete.** The durable delete intent is saved under the
  state lock, the guard is dropped for `blkdiscard`/`lvremove`, and a fresh
  critical section removes the record, delete intent and stale intents after
  revalidating the volume and the exact intent. A per-volume delete drive
  refuses a duplicate delete.
- **E2 (`2c5b065`) — create.** The durable create intent is saved under the
  state lock; `lvcreate` and its size-verifying `lvs` run without it; the
  final commit reacquires the lock, revalidates the same intent, inserts the
  record, drops the intent and saves once. A create takes the existing
  per-VG capacity reservation under the lock before releasing it and releases
  it (after bumping the allocation epoch) when the command returns. A
  create/delete structural drive map refuses a concurrent structural
  mutation of one volume.
- **This slice (`7204a53`) — worker handoff.** `create_volume` and
  `delete_volume` now run their synchronous LVM bodies through
  `run_blocking_body`, the same `block_in_place` handoff `grow_volume`
  already used. Before this, enough concurrent create/delete bodies could
  pin every async worker and starve reads, attaches, reports and detaches
  behind them. The inline fallback is kept for current-thread runtimes and
  `LocalSet` contexts.
- **Test coverage added.** The E1/E2 gate tests now exercise the shared
  drive map's cross-kind refusal (delete during create and create during
  delete) and prove the create capacity reservation is released on
  completion.

The measured slice changes only create and delete. **The timed mixed sweep
and the soak contain no create/delete calls** (their `per_op` keys are
attach, report, detach, grow, inspect, list and capabilities). Create and
delete appear in the untimed mixed-scenario setup/cleanup and in the
concurrency-1 micro phase. The release binary differs from `2c5b065` only in
the two create/delete wrappers in
`crates/volvisor-lvm/src/provider.rs`; the rest of the source diff at this
SHA is tests and docs. This report therefore does not present a sweep or
soak delta as a gain from the handoff, and it does not attribute any sweep
or soak delta to it.

## 2. Test evidence at the measured SHA

At `7204a53`, before the run:

- `cargo fmt --all --check` passes.
- `cargo clippy --workspace --all-targets --locked -- -D warnings` passes.
- `cargo test --workspace --locked` passes (`exit=0`), including the LVM
  tests (87 + 16 + 1 + 88 + 52).
- Deterministic gate tests park the fake `lvremove` and `lvcreate`. While
  parked, an attach on a different volume completes, the deleting/creating
  volume stays fenced, grow admission honors the create's reservation, a
  same-kind duplicate is refused, and the cross-kind create-vs-delete
  request is refused with the typed drive error.
- After the parked create completes, a 4 MiB create succeeds in the 8 MiB
  that remains. That 4 MiB demand plus the 4 MiB headroom fits only if the
  departed create's 1 GiB reservation was released.
- Negative controls: relaxing the shared guard to same-kind refusal makes
  both cross-kind assertions fail (`NotFound` for delete-during-create,
  `durable pending delete` for create-during-delete instead of the typed
  drive refusal). Leaking only the parked create's reservation makes the
  4 MiB create fail with `NO_SAFE_CAPACITY`. With the fix restored, the
  gate tests pass.

These are test evidence, not measurements. This harness does not inject
crashes or kill the daemon during a create/delete. The handoff's liveness
benefit is not measured here; the benchmark contains no concurrent
create/delete load.

c1 and c8 are modestly higher; c32 is roughly flat; **c128 fell 24.24% in
this sample**. The c128 throughput is completion-inclusive and the two runs
have different drain times:

- candidate: 18,423 ops over 39.799 s (462.899 ops/s);
- comparator: 25,441 ops over 41.639 s (610.988 ops/s).

The fall is not only a drain artifact. At the last sample at or before 30 s
(29.0 s), the candidate had completed 18,167 ops (625.8 ops/s) versus the
comparator's 22,972 (791.4 ops/s), −20.9%. Both denominators show a
substantial drop in this sample. Both are reported so neither denominator is
cherry-picked.

**Attribution.** The timed sweep contains no create/delete, and the release
binary differs from the comparator only in the two create/delete wrappers.
The drop is therefore not a direct effect of the changed operations. It
cannot be presented as a property of the handoff. However, the mixed
scenario does call create during untimed setup, so a runtime-level side
effect of the handoff cannot be excluded from a single sample.

To test that, a **non-evidence** diagnostic ran four `--skip-soak` runs
(no soak; micro, sweep, probes and pre-soak restart still ran)
alternating the two binaries: A = `7204a53` (same binary), B = `2c5b065`
(rebuilt at that source). The c128 results were A 626.011 and 439.497, B
432.752 and 427.457. The closest adjacent different-arm pair (B1 432.752 vs
A2 439.497) differed by 1.6%, but the other adjacent different-arm pairs
differed by 2.7% (A2→B2) and 31% (A1→B1), and consecutive runs of the same
arm (A1 626.011 vs A2 439.497) differed by 42%; the attach p50 moved with the
state (10.9 ms in A1, about 25 ms in the three later runs in both arms). The
measured run's 462.899 and an earlier same-SHA `--skip-soak` repeat of
519.539 both fall inside that range; see
[diagnostics/same-sha-repeat/README.md](diagnostics/same-sha-repeat/README.md).
The tier is dominated by time-varying host state in this lab on this day. See
[diagnostics/c128-variance/README.md](diagnostics/c128-variance/README.md).

That diagnostic is **not measured evidence**, was not used to select or
replace the measured sample, and supports no performance claim; it is used

small effect; it shows that one c128 sample cannot establish one. **No
throughput gain and no zero-regression claim is made for this slice.**

### 4.1 The c128 write p95 is not like-for-like

The aggregate write p95 is a quantile over all writes, so its meaning
depends on which operations occupy the top 5%. At c128:

| operation | candidate count | candidate p50 | candidate p95 | candidate max | comparator count | comparator p50 | comparator p95 | comparator max |
|---|---|---|---|---|---|---|---|---|
| attach | 1,697 | 25.190 | 238.779 | 713.4 | 2,392 | 13.584 | 179.590 | 930.8 |
| report | 1,697 | 22.248 | 206.629 | 809.1 | 2,391 | 13.184 | 185.523 | 839.0 |
| detach | 1,569 | 27.045 | 218.165 | 610.0 | 2,266 | 14.281 | 192.357 | 578.0 |
| grow | 386 | 9,719.410 | 18,123.642 | 29,550.612 | 399 | 10,390.696 | 22,079.170 | 39,574.976 |
| **write** | **5,349** | — | **9,151.103** | 29,550.612 | **7,448** | — | **4,297.266** | 39,574.976 |
| grow share of writes | **7.22%** | | | | **5.36%** | | | |

The candidate's slowest non-grow write is **809.085 ms**, below its
9,151.103 ms write p95; the p95 therefore lies in the grow distribution.
The comparator's slowest non-grow write is **930.797 ms**, below its
4,297.266 ms write p95; its p95 also lies in the grow distribution.

The candidate's write p95 rises because its grow share rises: the 5% tail
holds about 267 writes against 386 grows, so the p95 lands near the 31st
percentile of the grow distribution. In the comparator the 5% tail holds
about 372 writes against 399 grows, so the p95 lands near the 7th percentile
of the grow distribution. The candidate's grow p50 and p95 are both
**better** (10,390.696 → 9,719.410 ms; 22,079.170 → 18,123.642 ms). The
aggregate write p95 rise is a composition/quantile effect, not a
like-for-like write-latency regression. The non-grow write p95s did worsen
in this sample (attach +33.0%, report +11.4%, detach +13.4%), consistent
with the broad slowdown described above.

At c8/c32 the grow share is 0.09%/0.58%, so their write p95 values are
non-grow: c8 10.660 → 10.401 ms (−2.43%), c32 81.996 → 82.691 ms (+0.85%).
