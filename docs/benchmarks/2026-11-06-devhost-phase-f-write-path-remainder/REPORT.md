## 1. Scope and what changed

Phase F finishes the remaining `#62` write-path work and re-confirms that
the `#63`/`#64` code present in the tree behaves as implemented. It is a
hardening and verification batch, not a throughput or production claim.

At `2edcecd`:

- **F1 — move drive lock scope.** The same-VG move request and supervision
  path already released the provider state lock across every external CLI
  call. F1 adds deterministic regression tests that park the move's `lvs`
  observation and its `pvmove` start and show another volume's attach still
  completes; it proves the **existing** scope rather than claiming a new
  narrowing.
- **F2a — delete `lvs`.** Delete validates the request under the lock,
  snapshots the volume/VG/LV, drops the guard to run the `lvs` existence
  check, then reacquires and fully revalidates generation, VG, LV,
  lifecycle, pending grow and unsettled move before persisting the durable
  delete intent. A changed volume or incarnation fails closed; a
  failed/reordered revalidation never authorizes `blkdiscard`/`lvremove`.
- **F2b — create `vgs`.** Create samples `vgs` outside the lock under the
  existing allocation-epoch protocol, reserves the extent-rounded demand
  under the lock, re-checks the epoch after reserving, and persists the
  create intent in the same critical section. A stale sample retries within
  the bounded `CREATE_ADMISSION_ATTEMPTS = 32` budget and fails closed with
  the existing typed capacity/overload refusal rather than allocating
  against a stale sample. The reservation is released on every outcome.
- **F2c — failed-create compensation.** The durable-file classification
  stays under the lock. The uncommitted in-memory edit is rolled back, the
  guard is dropped for the compensating `lvremove`, and the lock is
  reacquired only to remove the volume/intent from memory and persist the
  cleared state. A landed final save keeps the volume and LV; a failed
  cleanup reports manual remediation; an unreadable durable file is treated
  as not committed; the original save error is never masked.

Three implementation residuals are **accepted**, not restructured: the
failure-only durable re-read in `persist_copying_record` stays under the
lock; startup `apply_delete_intents` runs the delete CLI under the startup
state lock (startup is single-threaded); and move's synchronous CLI calls
remain inline on async workers.

The measured slice's production changes are confined to create and delete;
F1 adds regression tests for the move path without changing its production
behavior. **The timed mixed sweep and the soak contain no create/delete/move
calls** (their `per_op` keys are attach, report, detach, grow, inspect, list
and capabilities).
Create and delete appear in the untimed mixed-scenario setup/cleanup and in
the concurrency-1 micro phase. This report therefore does not present a
sweep or soak delta as a gain from Phase F, and it does not attribute any
sweep or soak delta to it.

## 8. #63 verification — the retired-id filter and generation fence

These are **findings, not fixes**. ADR-0012 remains `Proposed`; `#63`
stays open.

**State shape.** `crates/volvisor-lvm/src/state.rs:98` is schema v3.
`:107` defines the 8 KiB-bit (1 KiB/volume) retired filter.
`:117-126` records that the filter is legacy, non-authoritative, and never
inserted into or consulted by the current provider. `:394-405` retains the
legacy field only so a v3 file decodes without loss. `:416-439` decodes
the legacy `retired_attachment_ids` vector and folds it into the filter.

**Fence.** `crates/volvisor-lvm/src/provider.rs:3812-3816` records that the
attachment generation is the detach/report fence and is strictly
increasing per volume. `:3821` sets the attachment's generation from the
consumed entry, `:3832` increments it on attach, and `:3894-3898` records
that detach does **not** tombstone the retired id. A delayed report with a
mismatched generation is refused with `STALE_GENERATION` at
`crates/volvisor-provider/src/semantics.rs:232-235`.

All ten listed tests pass:

- `v3_n_minus_one_fixture_imports_legacy_ids_and_upgrades_to_v3` (schema
  v3 import)
- `tombstone_fixture_preserves_retired_attachment_ids`
- `retired_attachment_filter_has_no_false_negatives_and_is_bounded`
- `malformed_retired_attachment_filter_is_rejected`
- `a_legacy_vector_is_merged_into_an_existing_filter_without_false_negatives`
- `a_noncanonical_filter_with_set_bits_is_never_treated_as_empty`
- `future_schema_version_is_refused_typed_without_rewriting`
- `zero_schema_version_is_refused_typed`
- `a_saturated_legacy_retired_filter_does_not_refuse_fresh_ids`
- `reattaching_a_consumed_id_fences_the_retired_instance_by_generation`

**Residuals recorded (not fixed):**

1. `provider.rs:3406` creates a volume with generation 1 and
   `provider.rs:5111` removes the record on delete. The strictly
   increasing fence is therefore **per-volume-lifetime**, not durable
   across delete + same-id recreate. A delayed report could match
   generation 1 if the same `attachment_id` is reused, and no test covers
   that case. (The report path does require the attachment id to match the
   current record, so the stale report must also reuse the id.)
2. The legacy wire vector at `state.rs:420` is still **unbounded at
   decode time**, even though the output filter is bounded. A hostile or
   corrupt v1/v2 file can present a large vector before the import runs.
3. A non-empty legacy filter is preserved on save (up to 1 KiB/volume)
   though it is never consulted, so a decode-only field can still occupy
   durable space.

Retry/backoff is at `:1029-1062` and its gate at `:853-869`; the one-frame

**Config wiring.** `crates/volvisord/src/config.rs:178-223` defines
`JournalConfig` and `to_retention`; validation is at `:1374-1401`;
`crates/volvisord/src/runtime.rs:76` opens with retention;
`examples/volvisor.toml:112-116` documents the defaults.

The listed retention/compaction/tombstone/config tests pass, including:

- `compaction_bounds_the_log_and_expires_evicted_operations`
- `the_tombstone_window_is_bounded_and_its_overflow_is_the_documented_contract`
- `tombstone_ring_deduplicates_duplicate_insertions_and_refreshes_their_position`
- `tombstone_ring_reinsertion_after_eviction_restores_only_the_newest_window`
- `tombstone_membership_is_consistent_across_a_snapshot_round_trip`
- `a_legacy_snapshot_with_duplicate_tombstones_restores_a_unique_ring`
- `is_tombstoned_matches_a_brute_force_reference_over_a_deterministic_sequence`
- `bounded_replay_evicts_and_compacts_before_serving`
- `a_failed_compaction_never_fails_the_durable_append_and_is_retried`
- `a_persistently_failing_compaction_backs_off_and_recovers_after_growth`
- `a_pinned_operation_is_never_evicted_while_its_retry_is_executing`
- `a_pin_interleaved_with_compaction_preserves_the_replacement_outcome_across_reopen`
- `compaction_evicts_to_fit_one_frame_instead_of_failing_forever`
- `journal_retention_defaults_are_bounded_and_mapped`
- `journal_retention_is_parsed_and_zero_bytes_disables_only_the_byte_trigger`
- `journal_retention_rejects_zero_bounds_and_unknown_keys`
- `scheduled_compaction_during_a_redrive_pin_preserves_the_latest_outcome_across_reopen`
- `scheduled_compaction_between_an_intent_and_outcome_keeps_the_operation_in_flight_across_reopen`

**Residuals recorded (not fixed):**

- **In-flight intents are never evicted** (`journal.rs:36,81,363`; the
  eviction at `:1743` is terminal-only). A long-running or stuck intent
  remains in memory and in the snapshot regardless of the retention bound.
- **"Expiry" is a count window, not a TTL.** An operation older than the
  newest `max_tombstones` evictions is indistinguishable from an unknown
  operation. A client retrying beyond the window can re-execute.
- **A persistent compaction failure backs off but leaves the log
  unbounded.** `journal.rs:1056` records the failure and a metric, but the
  backoff is a retry delay, not a size bound; the log keeps growing until
  compaction succeeds.
- **Configured bounds are soft.** The terminal registry may reach 2x
  `max_retained_operations` between compactions (`journal.rs:896-906`), and
  the one-frame planner can reduce effective retention
  (`journal.rs:1073-1124`). The configured values are upper bounds on the
  steady-state snapshot, not hard caps.
- **A 64-bit fingerprint collision can answer `OPERATION_EXPIRED`.** The
  tombstone ring stores exact 64-bit fingerprints; a different operation
  with the same fingerprint is treated as evicted and fails closed.
- **Observed high-water above the trigger.** The soak's journal high-water
  was 75,497,904 B, above the 64 MiB trigger and essentially identical to
  the prior run's 75,497,758 B. This is consistent with the documented
  post-compaction growth floor, not a new unbounded-log finding and not a
  hard-cap claim; the exact peak composition is not separately instrumented.
